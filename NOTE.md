# NOTE: what these results are and are not

**These results come from simulated data.** Every number in `drift-eval/` comes from synthetic
check-in histories generated by `simulate.py`. No real user data was used, read or touched.

**This is not clinical validation.** Nothing here shows that Evoki's drift alerts detect real
changes in sleep, mood or social contact, in older adults or anyone else. It does not support
any claim of clinical accuracy, sensitivity, specificity or safety.

**The numbers depend on assumptions.** False-alarm rates, detection rates, delays and precision
all change if the assumed noise, baselines, check-in rates, change sizes, change shapes or change
prevalence change. None of these parameters were estimated from real people. The noise ×
check-in-rate grid shows how strongly the results move with just two of them.

**Precision depends on the simulated prevalence.** The share of alerts that are correct depends
on the 50% prevalence of changed users in the simulation; with fewer real changes it would be
lower. For alerts whose first label is `moderate` (current app logic), there were **too few
episodes (n=49) to conclude** anything about their precision.

**One definition was changed after seeing results.** The true-positive window now runs from onset
to 14 days after the change is complete. It was changed after the first results, because alarms
during a gradual ramp had been wrongly counted as misses. The previous definition is still
reported next to it in `README.md` and `results/summary.md`.

**The variability-scaled threshold is a simulated idea, not a validated feature.** It was tuned on one
set of simulated users and tested on another set from the *same* simulator. It was compared with a
control: a single global threshold tuned the same way. On held-out users, retuning the global
threshold changed almost nothing. The variability-scaled rule did better than both, but as a trade-off:
fewer false alarms and lower detection for high-variability users, and more of both for steady
users. In this simulator, users in a group share the same noise level, so per-user and
per-noise-level thresholds cannot be told apart. The simulated noise is exactly the kind such a
rule is designed for, and the rule needs about 35 past check-ins while the app keeps 14. None of
this says how it would behave with real people.

**The groups are behaviour types, not demographics.** "Stable", "high variability", "sparse" and
"low baseline" describe answering patterns. They say nothing about age, sex, health condition or
any population group. "Worst group" means the worst simulated behaviour type.

**What this evaluation can support:**
- How the current detector logic behaves on inputs whose ground truth is known, as a software
  check.
- Comparisons between detector variants under the *same* assumptions: count vs calendar windows,
  with and without gating.
- Code-level findings that need no simulation: the adherence alert can never fire, alerts are
  saved again on every run, windows are counted in check-ins rather than days, and confidence is
  a three-level label based on data quantity only.

**What it cannot support:**
- Statements about real users' false-alarm rates or detection rates.
- Statements that an alert means a real decline, or that no alert means no decline.
- Use of "confidence" as a probability. It is a label for how many check-ins are in each window,
  and it is not calibrated.

**Scope:** the evaluation covers the Python port of `DriftDetection.detect` at app commit
`f389fc6383ae6416a84afea227639b4faa6f8dbb`. The port matched the Swift code on all 7 cross-checked
results. Any later change to the Swift detector requires re-checking the port.

Real-world evidence would need a separate study with real, consented data and appropriate ethical
and regulatory review. That is outside the scope of this folder.
